**Decisions:**

- **Two interfaces.** `PlatformApi` is what MFEs receive: branding, user, `permissions.can()`, `notify.toast()`, `audit.history()`. `ShellPlatformApi` extends it with the parts only the shell renders: inbox and reminders (bell), toast subscription, allowed apps (launcher). Together they cover all six platform modules. MFEs get the same object, typed as `PlatformApi`.
- **Sensitive actions are not in the browser contract.** Sending email/SMS/OTP, writing audit events, provisioning and role changes stay backend-only.
- **Contract version** `PLATFORM_API_VERSION = '1.0.0'`; additive changes only, a breaking change needs a new major version.
- **Async where data will come from a backend** (`audit.history`, inbox, reminders, allowed apps); `user` and `permissions.can()` are synchronous because they are loaded once at sign-in.
- **Libraries are bundled into each app, not shared at runtime.** Libraries are plain TypeScript/CSS source (no build step); Vite compiles them into each app. The bus still works across copies because all copies use the same `window`; `platform` is one object created by the shell and passed down.
- **One `theme.css` is both the fallback and the runtime theme.** Each app bundles it (fallback); in Step 9 the same file is also served from a brand server and loaded after the bundled copy, so its values win.
- **Only `services/platform.ts` knows it is a mock**; components get the platform through `usePlatform()`.
- **TypeScript project references** between apps and libraries are maintained by `nx sync` from `package.json` dependencies.
- **Mock role filtering:** replaced in Step 3b by per-app permissions and an Access Denied page.

**Verified:** `pnpm nx run-many -t lint test typecheck build` passes for all projects (14 tests); theme variables are in the shell's built CSS; `pnpm prettier --check .` passes.

Roles, permissions and app mappings live only in `mock-data.ts`.

**How a permission is checked (one mechanism):**

1. Users have roles; roles grant permissions written `action:resource` (`mockRolePermissions`).
2. Each application has its own permission: `access` on its app id, e.g. `access:react-a`.
3. `platform.permissions.can('access', appId)` answers it. Nothing else decides access:
   - `platform.apps.allowed()` (left nav + Portal Home tiles) filters the catalogue with `can('access', app.id)`;
   - the shell route guard `RequireAppAccess` calls `can('access', app.id)` before rendering an app route.
4. This is UX only. In production every backend API checks permissions again.

- **Login buttons have explicit labels** (`Sign in as User 1 (SALES)`) for screen readers.

## Step 4 – First React remote

**Done:** new app `apps/demo-react-a` (Nx name `demo-react-a`, port 4201). In development it also runs on its own with the mock platform (standalone mode); it is a Module Federation **remote** that exposes one component, `./App`. The shell is now the **host**: on `/react-a` (still behind the access guard) it downloads React A from `http://localhost:4201` at runtime and renders it with the host props `{ user, basePath, bus, platform }`.

**Concepts:**

- **Host / remote:** the host (shell) is the page the user opens; a remote (React A) is a separately built and served app whose code the host downloads at runtime. The shell bundle contains nothing of React A.
- **Exposes:** the list of modules a remote offers to hosts (`'./App': './src/App.tsx'`). The host imports it as `demoReactA/App`.
- **Remote entry / manifest:** `remoteEntry.js` is the remote's entry file; `mf-manifest.json` describes the remote (entry, exposed modules and their JS/CSS files, shared packages). The shell points at the manifest.
- **Shared singleton:** `react` and `react-dom` are declared `shared` with `singleton: true` in both apps, so only one copy runs on the page; `requiredVersion: '^19.3.1'` states which versions are acceptable. Sub-paths such as `react/jsx-runtime` and `react-dom/client` are shared automatically.
- **`shareStrategy: 'loaded-first'`:** use a shared package that is already loaded (the shell's React) before downloading another copy.

## Step 6 – Angular remote

**Decision before building (build options):** Module Federation is new to NPST, so no Angular team is assumed to use any federation tooling. The priority is that existing and future Angular teams can join **without migrating their build tooling**. Options considered: Vite + Analog plugin + `@module-federation/vite`; Angular CLI + Native Federation; Rspack (`@nx/angular-rspack`) + `@module-federation/enhanced`; Angular CLI webpack builder + MF plugin; and the standard Angular CLI build loaded as a plain ES module. All but the last require a build-tool change or a federation add-on. A spike confirmed the last one works, so it was chosen.

**Done:** new app `apps/demo-angular` (Nx name `demo-angular`, port 4203), a **standard Angular CLI project** (generated with `ng new`, default `@angular/build:application` builder, zoneless, standalone components). The shell mounts it on `/angular` through the mount contract, with the same props as React remotes; leaving the page destroys it.

**Concepts:**

- **Plain ES-module remote:** a normal `ng build` output whose entry file (`main-<hash>.js`) exports `mount` and `unmount`. Angular shares nothing with the React shell, so Module Federation (needed for the shared React copy) adds nothing here. React remotes stay on Module Federation.
- **Finding the entry file:** build tools add a content hash to file names, which changes on every build. The shell reads the current names from the remote's own built `index.html`, which every Angular build already produces, and imports the entry modules in page order.
- **Mount contract in Angular:** `mount` calls `createApplication()` with the props as an injection token (`MFE_PROPS`) and `APP_BASE_HREF = basePath`, then bootstraps the root component into an element inside the shell's container; `unmount` calls `ApplicationRef.destroy()`.
- **Router sync (`popstate`):** a router changing the URL with `history.pushState` is not announced to other routers on the page. The shell fires the standard `popstate` event after its own navigation, so the MFE's router re-reads the URL (e.g. clicking "Angular" in the nav while Angular shows page 2 returns it to page 1).
- **zone.js:** Angular's older change-detection library; it patches browser APIs (timers, promises, events) for the whole page, and cannot be removed once loaded. New Angular apps are zoneless by default.

**What an Angular team changes (app code only; `angular.json` builder unchanged):**

1. `main.ts` exports `mount(element, props)` / `unmount(element)` (about 25 lines) and still starts on its own when opened directly.
2. An injection token for the props; `APP_BASE_HREF` from `basePath`; a catch-all `**` route.
3. Styles in components using theme variables (global `styles.css` is not loaded inside the portal).
4. The server allows the portal's origin (CORS).

## Step 7 – Failure handling

**Done:** every remote, React (Module Federation) or Angular (plain ES module), now loads with a **time limit** and **one automatic retry**. If it still fails, or crashes while rendering, only its area shows "_App_ is not available right now." with a **Try again** button. The button starts a fresh load, so a remote that is back opens without reloading the page. The header, navigation and other apps keep working.

**Concepts:**

- **Timeout:** a remote whose server accepts the connection but never answers would otherwise leave "Loading…" on screen forever. Each attempt counts as failed after 8 seconds.
- **Retry:** one automatic retry after a 1-second pause covers short interruptions (e.g. a remote restarting during a deployment). More retries would only make the user wait longer before seeing the fallback.
- **Fresh load on "Try again":** the Module Federation loader forgets a failed attempt, so a new `import()` really goes back to the network; the shell keeps the load in state outside the Suspense boundary and starts a new one on "Try again".

| `apps/shell/src/remotes/registry.ts`                             | One `remotes` table for both kinds (`react` / `mount`), each with a `load` function                                   |
| `apps/shell/src/remotes/RemoteAppPage.tsx`                       | Starts the load with timeout and retry; React remotes read it with `use()`; "Try again" starts a new load             |

## Step 9 – Runtime theme

**Done:** a simulated **brand server** (`apps/brand-server`, port 4204) serves `theme.css`. The shell loads it at runtime after its bundled theme, so its values win. Changing one colour on the brand server changes the shell and all three MFEs after a page reload, with nothing rebuilt. If the brand server is down or hangs, the portal shows at once with the bundled theme (the fallback). No logo anywhere (unchanged rule).

**Concepts:**

- **Bundled fallback + runtime theme:** every app still bundles `libs/design-tokens/src/theme.css`, so it always has a complete theme. The runtime copy from the brand server is added later in the page, and for the same CSS variable the later definition wins.
- **Why MFEs follow automatically:** MFEs render inside the portal's page and use only theme variables (`var(--npst-…)`), so they read whatever the page defines. They do not load their own `theme.css` inside the portal (only in their standalone pages).
- **Non-blocking load:** the runtime stylesheet is added by script, not written into `index.html`, so a slow or unreachable brand server never delays the first render. Trade-off: on a slow connection the bundled colours can show briefly before the runtime theme applies.

## Step 23 – Branding Publish → brand server and runtime theme

**Done:**

- **Publish endpoint on the brand server** (`apps/brand-server/theme-endpoint.mjs`, a Vite middleware; no new dependency):

  | Request                   | Effect                                                               |
  | ------------------------- | -------------------------------------------------------------------- |
  | `PUT /themes/<appId>`     | Branding values (JSON) in; the server generates and stores the theme |
  | `GET /themes/<appId>.css` | The published theme; 404 when nothing is published                   |
  | `DELETE /themes`          | Removes every published theme (demo reset)                           |

  Published files live in `apps/brand-server/published/` (git-ignored demo data).

- **The server writes the CSS itself** (`theme-generator.mjs`) from validated values only:
  - hex colours;
  - fonts from the editor's list;
  - a radius between 0 and 32.

  It never stores CSS sent by a browser, and logos are never part of a theme (no-logo rule).

- **Portal theme:** "NPST Portal" (`app-portal`) is now in his application registry. Publishing its branding restyles the whole portal at runtime:
  - primary colour, sidebar, background, cards, text, borders;
  - heading font and radius.

  Body text keeps the portal font.

- **Application themes:** publishing Keka HR's or Deal Pulse's branding restyles only that application's area. The portal renders each application inside `data-app-theme="<appId>"`, and the theme is scoped to it. Inside the area, the NPST tokens the applications use are declared again, so they pick up the scoped values.
- **Light only:** published colours apply to the light mode; dark and high-contrast keep the portal's values.
- **Wiring in the portal (`services/brand-server.ts`):**
  - **Publish:** every way his Branding module publishes (Publish Theme, checker approval in the Approval Queue, Apply to all applications) sends the theme to the brand server and reloads it at once.
  - **Other tabs:** they reload when the branding data changes.
  - **Brand server down:** the administrator gets an error toast; the configuration is still saved.
  - **Reset demo data** (Settings): also removes the published themes.
- **Converter fix:** his pages also call `buttonVariants()` directly for links styled as buttons. There, the original does not merge classes (no tailwind-merge), so Tailwind's CSS order decides: the base radius and border win.
  - The converter now emits these few rules under a `npst-unmerged` marker.
